## Proof-target / precondition result

The Opyn v1 OptionsContract at `0x951D51bAeFb72319d9FBE941E1615938d89ABfe2` exposes a public storage getter `getVault(address payable) -> (uint256 collateral, uint256 oTokensIssued, uint256 underlying, bool owned)`. That is the strongest safe accessor already on-chain for proving the duplicate-exercise bug, since the second vault in the exploit's array is a real third-party vault and its collateral must drop when `msg.value` is reused across the loop.

Precondition outcome: a minimal `IOpynVault` interface was declared **inside the test file only** (no edits to `EVM/src/`). Strongest available proof target chosen, in priority order:
1. attacker profit (USDC strictly increases) — F4 unauthorized state transition
2. victim collateral loss (`getVault(victimVault).collateral` strictly decreases) — F3 invariant break

## Assertions added

In `test_attack()`, before the exploit:

```solidity
uint256 attackerUsdcRawBefore = usdc.balanceOf(attacker);
(uint256 victimCollateralBefore,,,) = opynVault.getVault(victimVault);
```

After the unchanged `addERC20CollateralOption -> exercise{value: 30 ether} -> removeUnderlying` sequence:

```solidity
uint256 attackerUsdcRawAfter = usdc.balanceOf(attacker);
(uint256 victimCollateralAfter,,,) = opynVault.getVault(victimVault);

assertGt(attackerUsdcRawAfter, attackerUsdcRawBefore, "attacker USDC must increase");
assertLt(victimCollateralAfter, victimCollateralBefore, "victim vault collateral must fall");
```

Notes:
- Attacker profit assertion uses raw 6-decimal USDC balances rather than the `/1e6`-truncated value used for logging, so sub-USDC profit is not silently dropped.
- Victim vault address `0x01BDb7Ada61C82E951b9eD9F0d312DC9Af0ba0f2` is the exact address already used by the exploit's `_arr[1]`; no new addresses, no balance manipulation, no flow changes.
- Conservative `assertGt` / `assertLt` chosen instead of exact-equality on a numeric delta because the precise per-iteration collateral decrement depends on Opyn v1 strike math and oracle state at fork time. The directional invariant is the safe, archival-RPC-independent claim.

## Whether the failure was RPC-related

**Yes.** The failure is `error code -32000: historical state ... is not available` returned from the upstream RPC during `vm.createSelectFork("mainnet", 10592516)`. It is not a revert from Opyn, USDC, or the new assertions, and it is not a compile error. Per Phase 7D rules this is classified as an RPC limitation, not a PoC failure. The patch compiles, formats cleanly, and is logically sound; an archival mainnet RPC is required to execute it.
