## 3. Assertions Added

Five exact equality assertions were added inside the existing
`function test()` body, around the unchanged exploit flow.

Captured pre-state (locals, before `propose`):

- `address attackerEOA = 0xb4c79daB8f259C7Aee6E5b2Aa729821864227e84;`
  (the EOA encoded in the proposal calldata's `approve` argument)
- `uint256 govBalanceBefore = build.balanceOf(address(BuildGovernance));`
- `uint256 attackerThisBefore = build.balanceOf(address(this));`
- `uint256 allowanceBefore = build.allowance(address(BuildGovernance), attackerEOA);`

Assertions, immediately after `BuildGovernance.execute(8, ...)`:

- `assertEq(allowanceBefore, 0)`
  — pre-state sanity: no prior BuildGovernance → attacker approval.
- `assertEq(build.allowance(address(BuildGovernance), attackerEOA), type(uint256).max)`
  — **F4**: proposal calldata is `approve(attackerEOA, max)` and
  `execute` runs with `msg.sender == BuildGovernance`, so the BUILD
  token's allowance from BuildGovernance to the attacker EOA must be
  `type(uint256).max` immediately after `execute`.
- `assertEq(build.balanceOf(address(BuildGovernance)), govBalanceBefore)`
  — **execute granted approval only**: the treasury balance must
  still be intact before the explicit `transferFrom`.

Assertions, immediately after the final
`build.transferFrom(BuildGovernance, this, balance)`:

- `assertEq(build.balanceOf(address(BuildGovernance)), 0)`
  — **F2**: BuildGovernance treasury fully drained.
- `assertEq(build.balanceOf(address(this)), attackerThisBefore + govBalanceBefore)`
  — **F1**: attacker's BUILD balance grew by exactly the pre-drain
  treasury balance.

Two short comments mark the proof targets (`Phase 7B / F4`,
`Phase 7B / F2`, `Phase 7B / F1`). No other comments were added.

### 5.1 Was the failure RPC-related?

`14_235_712`. The failure is in `vm.createSelectFork` during `setUp()`,
not in any of the patched assertions. None of the five new assertions
were reached. Per the rules of this phase, this is classified as an
**RPC limitation, not a PoC failure.**

### 5.2 Did the assertions execute?

No. Test reverted in `setUp` before the test body could run.

### 5.3 Static review still valid?

Yes. The patch:

- compiles under the project's solc configuration (`forge build`
  reports compiler success with only the pre-existing
  `erc20-unchecked-transfer` lint at line 71 — same warning class as
  pre-Phase-7B, just shifted lines because of the inserted snapshot
  block).
- passes `forge fmt --check`.
- does not change exploit flow, attacker actions, token addresses, or
  governance call ordering.
- expresses the F4 / F2 / F1 invariants as exact equalities tied to
  values already used by the unmodified flow (`type(uint256).max` and
  `govBalanceBefore`), so any false positive would also indicate a
