## 3. Exact Assertions Added

In `EVM/test/2017-11/Exploit_2017-11.t.sol`, inside `testExploit()`,
immediately around the existing `WalletLibrary.kill(address(this));`
call:

```solidity
bool isowner = WalletLibrary.isOwner(address(this)); // you are owner of contract now
assertTrue(isowner);

// F4/F7 proof target: pre-Cancun SELFDESTRUCT clears bytecode in-tx.
assertGt(address(WalletLibrary).code.length, 0, "target/library code should exist before exploit");
WalletLibrary.kill(address(this));
assertEq(address(WalletLibrary).code.length, 0, "target/library code should be removed after exploit");

WalletLibrary.isOwner(address(this)); // contract destroyed, return 0
```

The pre-existing `assertTrue(isowner)`, the existing `WalletLibrary.kill(address(this))` call, and the trailing `WalletLibrary.isOwner(address(this))` debug call are preserved exactly as they were. The patch is purely additive: two `code.length` reads and one extra comment line.

### Why these assertions are safe

- `address(...).code.length` is a pure observer; it cannot affect the state of the WalletLibrary contract or change the outcome of `kill`.
- The literal `0` post-condition is exact under pre-Cancun SELFDESTRUCT semantics: at fork block `4501735`, Cancun (block `19426587` on mainnet) is far in the future, so SELFDESTRUCT clears the contract's code in the same transaction.
- Both compares are exact equalities/strict inequalities against constants — zero false-positive surface. A passing assertion proves the destructive call landed; a failing assertion proves it did not.

## 6. Why Failure Is RPC-Related, Not PoC-Related

The error path is unambiguous:

1. The error message comes from `vm.createSelectFork`, which is the very first line of `setUp()`. No test code beyond `cheats.createSelectFork("mainnet", 4_501_735)` ran.
2. The error code is `-32000` with body `historical state ... is not available` — the canonical Geth/Erigon response when an RPC node has pruned the trie state for the requested block.
3. The same RPC alias works for recent blocks (Phase 4A smoke-test artifacts), so the failure is block-age dependent, not config-broken.
4. The address Foundry tried to read first (`0x1804c8...`) is an internal precompile/genesis check, not the WalletLibrary; the failure is fork plumbing, not PoC logic.

A node that does serve archival state at block `4501735` (Erigon/Reth/Geth `--syncmode full` with archive flag, or a paid archival provider) is sufficient to execute the PoC. No code change to the PoC itself is needed.

**Recommended next target: `2018-04-bec-token` (BeautyChain `batchTransfer` overflow).**

Justification, drawn from Phase 6B section 4.2:

- Phase 6B ranks it 2nd, immediately after this PoC, on smallest-blast-radius criteria.
- The current test has **zero assertions** — only `emit log_named_decimal_uint`. A passing test today does not prove the overflow even fired. Any assertion is a strict improvement.
- The canonical fingerprint is exact: per-receiver mint of `type(uint256).max / 2 + 1`, and the sum of two attacker balances exceeding `totalSupply()`. Both are exact-equality / strict-inequality compares against literal exploit input — zero false-positive surface, identical to the 2017-11 patch shape.
- The patch surface is small: capture two `balanceOf` snapshots before `bec.batchTransfer(...)`, two after, plus one `totalSupply()` read. No prank, no new external call to the exploit target, no fork-block change.
- Exploit flow is unchanged. The `batchTransfer` call itself is not touched; only observers wrap it.
- Like 2017-11, runtime verification will be RPC-blocked on public endpoints (block `5483642` is archival), so the same "RPC limitation, not PoC failure" rule applies.

A single sub-phase (Phase 6D) should land that patch, run the same validation chain, and stop. **Do not** start it as part of 6C.
