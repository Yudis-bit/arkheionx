## Phase 1 — Audit summary (read-only)

### Repository purpose, as advertised

Public README and web copy claim:

- A multi-VM exploit archive covering EVM, SVM, and MoveVM.
- "Deterministic Proof-of-Concept exploits for high-severity Web3 vulnerabilities."
- Working CI (`EVM_Tests-passing`, `SVM_Tests-passing` badges).
- A vulnerability registry with severity classification, embargoed research, and
  attack taxonomy.
- A "DeFi Security Vault" with services ("Protocol Audits", "PoC Development",
  "Hire Yudis-bit" CTAs).

### Repository purpose, as actually implemented

- **EVM**: 18 PoC folders under `EVM/test/`, each containing one `.t.sol` file
  ported from `SunWeb3Sec/DeFiHackLabs`. Most use `vm.createSelectFork` against
  pinned mainnet block numbers. This is the only part of the repo with real
  technical content.
- **SVM**: One file (`SVM/tests/exploit.ts`) containing an empty `it("hijacks state", ...)`
  block. No Anchor program. Not a PoC. Effectively a placeholder.
- **MoveVM**: One file (`MoveVM/sources/exploit.move`) containing an empty
  `public entry fun execute(attacker: &signer) {}`. Not a PoC.
- **Metadata**: `web/public/metadata.json` is generated by
  `generate_web_metadata.py`, which invents "educational insights" by rotating
  through a hardcoded list of generic phrases.
- **CI**: Single workflow at `.github/workflows/foundry.yml` runs `forge fmt`,
  `forge build`, `forge test` from repo root, but the Foundry project lives
  in `EVM/`. Without `working-directory: EVM`, the workflow cannot succeed.
- **Web**: Next.js app with fake stats ("Active Research: 4", "Chain Support: 12"),
  hardcoded "Hire Yudis-bit" CTAs, and severity derived from `id <= 3`.

### Gap between promise and implementation

| Claim | Reality |
|---|---|
| Multi-VM archive | EVM-only in any meaningful sense |
| `SVM_Tests-passing` badge | No SVM tests exist; badge is decorative |
| "Vulnerability Registry" with 2 entries | EVM/test/ has 18 entries; registry is stale |
| "Embargoed Research" with placeholder rows | No evidence in repo of actual embargoed work |
| "Educational insights" per PoC | Auto-generated rotating filler, not real analysis |
| CI works | Workflow paths are wrong; would fail or be skipped |

### Highest-impact issues

1. README registry contradicts the actual `EVM/test/` tree.
2. CI workflow's `working-directory` is wrong.
3. Web copy contains invented metrics and unverified service CTAs.
4. SVM and MoveVM are advertised but not implemented.
5. `poc_factory.py` runs `git commit` and `git push` automatically when forge
   tests pass — unreviewed code can land on `main`.
6. Auto-generated "educational insights" are AI-flavored filler that contradicts
   the research-grade brand.

### Things that already work

- EVM PoCs themselves are real: pinned forks, deterministic asserts, attribution
  comments to original analyses.
- `foundry.toml` correctly uses `via_ir`, optimizer, solc 0.8.20.
- Repo cleanly separates VM directories.
- `.gitignore` already excludes `lib/`, `node_modules/`, `.env`, etc.
- Commit history is readable (one PoC per commit).

### Things that make the repo look amateur

- README badges that aren't tied to real CI.
- Fake stats on the web landing.
- "Hire me" CTAs that overclaim service capability.
- Auto-generated "insights" that read as AI filler.
- Inconsistent folder naming (`YYYY-MM/` instead of `YYYY-MM-Protocol/`).
- Inconsistent file naming (`Exploit_YYYY-MM.t.sol`, not protocol-named).
- `build` empty file at repo root.
- Embargoed research table populated with vague placeholders.

### Things that already make the repo credible

- Real attribution to original PoC authors and post-mortems.
- Clean PoC structure with `setUp` + `testExploit`.
- `via_ir` build pipeline (matches modern Foundry idioms).
- Clear single-PoC-per-commit history.

### Immediate red flags

- `poc_factory.py` auto-commit + auto-push on green test (line 213-222).
- README claims "SVM Tests passing" — there are no SVM tests.
- "Hire Yudis-bit" buttons published before any audit experience is documented.

### Reproducibility concerns

- No documented archival RPC requirements.
- Only one RPC alias (`mainnet`) in `foundry.toml`; some real-world PoCs require
  Base, Arbitrum, Optimism, BNB, etc. (Repo currently only ships ETH-mainnet
  forks; non-Ethereum PoCs are filtered out by `poc_factory.py`.)
- No documented expected `forge test` command per PoC.
- No `.env.example`.

### Branding concerns

- Two competing identities: "Yudis-bit | The DeFi Security Vault" (web app)
  vs "Arkheionx" (README). Need a single canonical brand.
- "DeFi Security Vault" sounds product-marketing; "Arkheionx Vault" sounds
  research-archival. We are committing to the latter.

### Suggested rebuild order

1. Rebuild log (this file).
2. Docs skeleton (`docs/`) — sets the standard before changing code.
3. Fix CI working-directory.
4. Add metadata schema + registry generator.
5. Rebuild README from generated registry.
6. Web app: drop fake stats, drop service CTAs, consume canonical registry.
7. Refactor `poc_factory.py` to dry-run by default, no auto-push.
8. Honest VM support docs (SVM/MoveVM clearly marked template).
9. Issue/PR templates.
10. Final report.
