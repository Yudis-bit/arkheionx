# PoC Maturity Model

This document defines a six-level maturity ladder for every entry in
`metadata/registry.json`. Maturity is intentionally separate from
`assertion_quality`, `reproducibility`, and `verification_status` — it
combines them into a single readiness signal so that a reviewer can
look at one number and know what is left to do.

The maturity index is generated by `scripts/poc_maturity_index.py` into
`reports/poc_maturity_index.md`. Maturity is not stored in the registry
because it is fully derivable from the existing fields.

## Why a ladder

A PoC that compiles is not verified. A PoC that logs balances is not
proof. A PoC that asserts attacker profit but cannot run on a public
RPC is in a different bucket from a PoC that has been replayed against
a pinned archival fork. The ladder gives each of those a name.

The point is to make the gap to "research-grade" visible per entry,
without pretending the gap is smaller than it is.

## Levels

### L0 — Raw Replay

The PoC compiles and the exploit shape is present, but proof is weak.
Typically only `console.log` of balances or inherited balance modifiers.
A green run says nothing about whether the exploit triggered.

Required to leave L0:

- Hard `assert*` calls covering at least one required family for the
  category (`docs/ASSERTION_STANDARD.md`).

### L1 — Structured Metadata

The registry entry identifies the protocol, chain, fork block, root
cause, attacker path, and broken invariant. The metadata is consumable
by the scoring tools without `unknown` placeholders for the fields
listed in `docs/METADATA_SCHEMA.md`.

Required to leave L1:

- All required metadata fields populated (no `unknown`).
- Severity, category, and reproducibility status set.
- At least one external reference (post-mortem, advisory, or original
  PoC author).

### L2 — Assertion-Hardened

Hard assertions cover the documented exploit primitive: attacker
profit, victim/protocol state damage, the broken invariant, or the
unauthorized control change. The PoC fails loudly if exploit logic
regresses. This is **static** readiness — the assertions are sufficient
on paper. Runtime confirmation has not necessarily happened.

`assertion_quality` of `medium` reaches L2 if the medium assertion is
on post-state and not just a precondition. `strong` always reaches L2.

Required to leave L2:

- A recorded fork run, public or archival, with output captured in
  `reports/verification/<id>.md` or in `latest_public_rpc_status` /
  `latest_public_rpc_notes` on the entry.

### L3 — Public RPC Smoke-Tested

A public RPC fork attempt has been recorded. The result is one of:

- `public-rpc-pass` — `setUp()` and exploit body executed without
  reverting.
- `public-rpc-not-archival` — public RPC could not serve historical
  state for the pinned block. This is an RPC limitation, not a PoC
  defect, and is recorded honestly.
- `public-rpc-rate-limited` / `public-rpc-unstable` — endpoint refused
  or dropped during run; recorded for re-attempt.

A `public-rpc-pass` does not promote the entry past L3. Public RPC
smoke tests cannot guarantee the assertions are correct against the
real historical state — only that the test wires up.

Required to leave L3:

- Pinned-fork run on an archival RPC at the entry's `block_number` and
  `rpc_alias`, with meaningful assertions, with output captured in
  `reports/verification/<id>.md`.

### L4 — Archival Verified

`forge test` runs to green against a pinned archival fork on the
recorded branch. Verification report under `reports/verification/`
contains real run output, not a generated stub. `verification_status`
is `verified`. `reproducibility` is `deterministic-confirmed`.

L4 is the bar at which the README's "deterministic-confirmed" count
goes up.

Required to leave L4:

- Written root-cause case study with patch lesson and auditor checklist
  exercise — the entry is teachable, not just runnable.

### L5 — Research-Grade Case Study

L4 plus:

- Long-form root-cause writeup recorded under
  `reports/case-studies/<id>.md` (path reserved; created when entries
  reach this level).
- Patch lesson documented and cross-referenced from
  `docs/ROOT_CAUSE_PLAYBOOK.md` if it introduces a new pattern.
- Auditor checklist for the entry's category exercised against the
  PoC, with findings recorded.
- Reference quality verified: at least one independent source besides
  the protocol's own post-mortem; archived links where the source has
  decayed.

L5 is the level at which an entry is suitable to cite in audit work or
education without further review.

## Computation rules

The script applies these rules in order. The first matching rule wins.

1. If `verification_status == "verified"` AND
   `reproducibility == "deterministic-confirmed"` AND
   a real verification report exists AND
   a case study file exists at `reports/case-studies/<id>.md` — **L5**.
2. Else if the same conditions minus the case-study file — **L4**.
3. Else if a verification report exists with non-stub run output, OR
   `latest_public_rpc_status == "public-rpc-pass"` — **L3**.
4. Else if `assertion_quality in {"strong","medium"}` — **L2**.
5. Else if metadata required fields populated — **L1**.
6. Else — **L0**.

`public-rpc-not-archival`, `public-rpc-rate-limited`, and
`public-rpc-unstable` are recorded but do not promote the entry past
L2. They are RPC limitations, not progress.

## Relationship to other signals

| Signal | Maps to |
|---|---|
| `assertion_quality` | gates L2 |
| `latest_public_rpc_status` | observed; does not gate L3 alone |
| `verification_status` | gates L4 |
| `reproducibility` | gates L4 |
| Case study file | gates L5 |

Maturity does not weaken any individual signal. It composes them.

## What maturity is not

- Not severity. A critical-severity exploit at L0 is still critical;
  the maturity number describes what we have proven, not what the
  incident did.
- Not score. `score_pocs.py` produces a static-readiness percentage;
  maturity reports the discrete level the PoC is camped at.
- Not a target. The goal is not "every PoC at L5". Some incidents
  cannot reach L5 within the public record. Honest L2/L3 is fine.

## Roadmap

The current corpus is dominated by L2 entries blocked at the L3 → L4
boundary by archival RPC availability. Once an archival mainnet RPC is
configured for the maintainer:

- Several L2 entries should clear L3 with one fork run each.
- A subset will clear L4 once the verification reports are written
  with real output.
- L5 work begins when ≥3 L4 entries exist and a case-study format has
  been validated.
